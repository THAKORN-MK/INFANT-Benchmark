# แบบออกแบบ: benchmark Sinc-Mamba-KAN จากบทความ

วันที่: 17 พฤศจิกายน 2026  
สถานะ: แบบเสนอเพื่อขออนุมัติ ยังไม่ใช่ผลการทดลอง

## วัตถุประสงค์และทางเลือก

สร้าง benchmark ใน `D:\INFANT Benchmark` โดยใช้ข้อมูลที่ผู้ใช้จัดเตรียมและวิธีจากบทความ Sinc-Mamba-KAN ให้ใกล้เคียงที่สุด เพื่อนำไปเปรียบเทียบกับโครงการ `D:\INFANT CRY` ในภายหลัง ผู้ใช้เลือกแนวทางนี้แทนการรอ source code ผู้เขียนหรือเปลี่ยนบทความ เพราะต้องการใช้ dataset เดียวกัน การเปรียบเทียบที่ยุติธรรมต้องตรวจสอบทั้งตัวไฟล์และวิธีแบ่งข้อมูล ไม่อาศัยชื่อชุดข้อมูลเพียงอย่างเดียว

ผลผลิตเป็น independent paper-based implementation ไม่ใช่โค้ดต้นฉบับ และห้ามอ้างว่าตรงบทความทุกขั้นตอน ห้ามแก้ข้อมูลเสียงต้นฉบับ ห้ามฝึกโมเดลแทนผู้ใช้ และห้าม push

## การดำเนินการ

1. ใช้รายงาน `docs/replication_audit.md` และ PDF เป็นต้นทาง ตรวจสอบอีกครั้งก่อนลงมือ แยกค่าที่มีหลักฐานชัด ค่าที่ต้องตั้งสมมติฐาน และสิ่งที่ยังขาด พร้อมบันทึกเหตุผลและหน้า PDF
2. ตรวจโครงสร้าง dataset, labels, tiers, metadata, สิทธิ์ใช้งาน, ไฟล์ซ้ำ และความสามารถในการระบุแหล่ง/ตัวทารก โดยไม่แก้ข้อมูลเดิม ห้ามยืนยันว่าเป็น dataset เดียวกันโดยดูเพียงจำนวนไฟล์ ไม่แก้ label หรือทิ้งไฟล์ที่ขัดแย้งโดยพลการ
3. สร้าง preprocessing และสถาปัตยกรรมตามหลักฐานที่มี ได้แก่ waveform branch Sinc + convolution + Mamba, feature branch สกัดคุณลักษณะและเลือกจาก training fold เท่านั้น และ KAN classifier ตามค่าที่บทความระบุ กรณี 213 descriptors หรือรายละเอียดอื่นที่ไม่ครบ ต้องระบุ schema พารามิเตอร์และวิธีเลือกสมมติฐานให้ครบ หากใช้ feature ทดแทนต้องระบุว่าเป็น proxy ไม่อ้างว่าเป็น feature เดียวกันของผู้เขียนหรือเติมตัวเลขแบบไม่เปิดเผยเพื่อให้ได้ 213
4. เตรียม pipeline training และประเมิน 5-fold พร้อมกำหนด seed, split, วิธีเลือก checkpoint และบันทึก deviation โดยใช้ inner validation หรือกำหนดจำนวน epoch ล่วงหน้า ห้ามใช้ outer fold ที่ประเมินในการเลือก checkpoint; ถ้าไม่มี infant ID ที่พิสูจน์ได้ ห้ามอ้าง infant-disjoint
5. จัดทำการทดสอบด้วยข้อมูลจำลองและตรวจเส้นทางการทำงาน โดยไม่ fit หรือ train โมเดลจริง ไม่ติดตั้งทับ environment เดิมโดยอัตโนมัติ บันทึก dependencies, ตรวจสิทธิ์ขององค์ประกอบ และข้อจำกัดของ GPU/Mamba ให้ตรวจสอบได้
6. จัดทำเอกสารวิธีติดตั้ง ตรวจ dataset คำสั่งที่ให้ผู้ใช้รันเอง รายการผลลัพธ์ และข้อจำกัด พร้อมระบุว่า dataset จริงยังไม่ถูกนำเข้าและยังไม่มีผลเทรน

## เกณฑ์ก่อนประเมินและเปรียบเทียบจริง

- ตรวจสอบ dataset และ provenance ก่อน: สำเนาที่เคยตรวจพบ 198 กลุ่ม byte-identical และในนั้น 3 กลุ่มมี label ข้ามคลาส ต้องตรวจหลักฐานก่อนเลือกวิธีจัดการ
- ตกลง protocol และวิธีรับมือข้อมูลขัดแย้งก่อนรันจริง พร้อมระบุผลกระทบต่อความเทียบเคียงกับบทความ
- แยก protocol ทำซ้ำตาม paper จาก protocol เปรียบเทียบกับโครงการเดิมซึ่งอาจใช้ split ต่างกัน และรายงาน deviations ของแต่ละ protocol การเปรียบเทียบที่ยุติธรรมต้องใช้ไฟล์, labels, partitions และตัวชี้วัดที่เทียบกันได้ ตรวจประวัติการใช้ test เดิม และไม่ใช้ test ที่ถูกใช้เลือกหรือปรับโมเดลเป็นหลักฐานผลยืนยันโดยไม่เปิดเผย
- คะแนนของ paper เป็นเพียงผลที่ตีพิมพ์ ไม่ใช่ผล benchmark ของ implementation นี้

รายละเอียดเริ่มต้นและรายการค่าที่ยังไม่ทราบดู `docs/replication_audit.md` และ `configs/paper_full_capacity.json`
